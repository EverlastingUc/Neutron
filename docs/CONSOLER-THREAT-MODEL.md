# Consoler Threat Model

Status: v0.1 design baseline. Consoler is a defensive integration toolkit, not an anti-DevTools mechanism.

## 1. Security objective

Consoler aims to help application teams reduce accidental disclosure through production diagnostics and report selected application-detected integrity or state anomalies to their own trusted backend.

**Consoler cannot prevent hacking, stop a user from opening browser developer tools, or make browser-delivered code trustworthy.** The browser and all client-side state are controlled by the user. Client-side checks are friction and telemetry only; they are never authorization controls.

## 2. Assets

Applications integrating Consoler may need to protect:

- User data and private application records.
- Account sessions and authentication credentials.
- Privileged operations and entitlement decisions.
- API availability and service capacity.
- Internal diagnostics that might reveal implementation details.
- User privacy and the integrity of security telemetry.

Consoler itself must not receive passwords, access tokens, session cookies, private keys, payment data, page contents, keystrokes, or unrelated browsing data.

## 3. Trust boundaries

| Boundary | Trust level | Required treatment |
|---|---|---|
| Browser JavaScript and DOM | Untrusted | Assume users can inspect, alter, replace, or bypass it. |
| Client storage and client telemetry | Untrusted | Never use as proof of identity, permission, or integrity. |
| Network requests | Untrusted input | Authenticate, authorize, validate, and rate-limit on the server. |
| Application server | Trusted only after hardening | Enforce policy and make all sensitive decisions. |
| Database and secret store | Trusted infrastructure | Restrict access and keep privileged secrets server-side. |

## 4. Attacker capabilities

Assume an attacker can:

- Open DevTools and inspect all delivered HTML, CSS, JavaScript, and network traffic.
- Change JavaScript variables, DOM nodes, local/session storage, and client-side feature flags.
- Call public APIs directly without using the application's UI.
- Modify, replay, reorder, or forge client requests and telemetry.
- Disable or replace Consoler in the browser.
- Automate requests and attempt resource exhaustion.
- Exploit application vulnerabilities such as XSS or broken access control.

Consoler must not attempt to defeat these capabilities with keyboard traps, debugger loops, page freezes, obfuscation, stealth, or destructive behavior.

## 5. Threats and required controls

| Threat | Primary control | Consoler's role |
|---|---|---|
| User edits a hidden/disabled UI control | Server-side authorization for every sensitive operation | May report a host-app-detected state anomaly; signal is untrusted. |
| Forged API request | Authentication, authorization, schema validation | No client-side guarantee. |
| Client entitlement/role changed | Derive permissions from server-side identity and policy | Never treat client role flags as authority. |
| Replay or automated abuse | Nonces/idempotency where appropriate, rate limits, abuse monitoring | Optional anomaly signal only. |
| Sensitive production logs exposed | Build-time log hygiene, redaction, server-side logging | Provide opt-in development-only diagnostics in a future release. |
| Telemetry abuse or spoofing | Server-side validation, quotas, correlation, low-trust scoring | Emit only small, typed, application-requested signals. |
| XSS or compromised dependency | Output encoding, CSP, dependency hygiene, secure development | Out of scope for client-side prevention; telemetry cannot repair XSS. |

## 6. Consoler boundaries

### In scope

- Explicit, opt-in reporting of a small set of application-detected signals.
- A bounded and typed signal schema.
- Development/production diagnostic separation.
- Examples of server-side authorization, validation, and rate limiting.
- Clear privacy controls and tests for missing APIs and callback failures.

### Out of scope

- Disabling DevTools or blocking F12/right-click/keyboard shortcuts.
- Detecting DevTools as a reliable security fact.
- Preventing inspection, modification, copying, or replay of client code and requests.
- Hiding secrets or privileged business logic in JavaScript.
- Automatically banning, locking, or punishing users based on client telemetry.
- Keylogging, session scraping, page-content collection, stealth, persistence, or anti-analysis behavior.

## 7. Signal handling policy

A Consoler signal means only: "the application reported that a local invariant or expected transition did not hold."

It does not mean a user is malicious. Signals may be forged, suppressed, duplicated, or generated by bugs, extensions, browser differences, or accessibility tooling.

The receiving server must:

1. Validate the event schema and enforce payload/rate limits.
2. Treat the event as low-confidence telemetry.
3. Correlate it with trusted server-side events before taking action.
4. Never grant or deny access solely because of a client signal.
5. Avoid retaining telemetry longer than the application's documented purpose requires.

## 8. Privacy requirements

- Reporting must be opt-in and documented by the integrating application.
- The default payload contains only a version, a finite event type, and an application-defined short code.
- No automatic collection of user content, URLs, DOM snapshots, keystrokes, tokens, or arbitrary exception objects.
- No network transmission is performed by Consoler itself.
- Integrators must document consent, retention, access, and deletion practices for any backend telemetry they add.

## 9. Residual risk

A determined user can remove or bypass any browser-side Consoler code. Client-side signals are not cryptographic attestation. The only reliable security boundary for privileged application behavior is the server and its backing services.

## 10. Acceptance criteria

A conforming implementation must:

- Default to no monitoring and no network activity.
- Require explicit application calls to emit signals.
- Validate and bound all signal fields.
- Avoid collecting sensitive or unrelated user data.
- Fail safely if callbacks or browser APIs are unavailable.
- Include tests proving that client signals are not represented as trusted authorization decisions.
